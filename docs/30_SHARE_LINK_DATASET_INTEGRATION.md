## 2. Families and counts

### 2.1 Counting ambiguity found and corrected

In the Task 1 draft, each `s02` "minimal pair" was a **triple** (absent / same access / other
access). This had three problems:
- "8 scenarios" meant 8 pairs in `s01` but 8 triples in `s02`, so "pairs" and "states" were
  ambiguous.
- Same access and other access are both R at h3, which breaks the dataset's pair contract (two
  members whose h3 labels differ, `validation._check_pairs`).
- The horizon-sensitive member could not be excluded on its own.

`s02` is now split into two pair families. The rule is: **one base scenario = one minimal pair
= two states = two records** (one render style per scenario, shared by both members).

| Family | Action (identical within the pair) | Pivot (pair members) | Expected labels at h = 1/2/3 (declared, not enforced) | Scenarios / pairs / states |
|---|---|---|---|---|
| `s01_link_revoke_address_kind` | `revoke_share_link(<target>)` | address custom / generated | R R R / P P P | 7 / 7 / 14 |
| `s02_link_create_history` | `create_share_link(path, access, <custom address>)` | revoked custom record absent / same access | P P P / R R R | 7 / 7 / 14 |
| `s03_link_create_access_history` | same as `s02` | absent / other access | P P P / P P R | 7 / 7 / 14 |
| **Total** | | | | **21 / 21 / 42** (3 families; 42 records if all pass) |

**Render styles.** `kv`, `prose` and `compact` are cycled by scenario index, giving
18 / 12 / 12 records. No style is test-only, because there is no split.

**Background.** These vary across scenarios but are identical within a pair:
- 1–2 files;
- 0–2 distractor links;
- link order;
- file revisions;
- the task template.

**Planner.** It now rejects a draw if *either* member repeats the coarse canonical structure of
*any* earlier planned state in the pilot. Before, the check was per family and per pair key.
The result is 42 distinct strict and 42 distinct coarse scenarios.

## 4. Prompt builder 1.1.0 and version-aware loading

**Builder 1.1.0** (`src/adnn/dataset/prompting_v11.py`, Task 1):
- It appends a `Share links` section to the unchanged 1.0.0 text. The section covers active
  **and** revoked records with id, file, access, address and custom/generated, and is always
  present.
- The tool list is `tool_specs_for(state)`.
- It uses the 1.0.0 templates, stamped `1.1.0`.

**Registry** (`src/adnn/dataset/prompt_versions.py`, new). It maps each version to its renderer
and builders, and records whether that version renders links. Unknown or missing versions raise
`UnsupportedPromptBuilderError`, naming the version and the supported ones.

**`api.load_dataset`:**
- The manifest's version, if present, must be supported.
- Every record's version must be supported and must equal the manifest's version. A mixed
  dataset raises `DatasetIntegrityError`.
- Prompts are rebuilt and hash-checked with the record's own builder
  (`LoadedDataset.prompt_builder`).
- `"split": null` is accepted: `split_of` returns `"unsplit"` and `iter_split` raises.
- The legacy path is byte-for-byte the same. The pilot loads with 165/45 train/test records,
  and its stored prompt hashes rebuild through the API.

**Validator** (`adnn.dataset.validation`):
- It re-renders state text and rebuilds prompts with the record's builder.
- An unsupported version is an error.
- A 1.0.0 record whose state has links is an error, because 1.0.0 would hide them.
- `split=None` skips split checks with a warning.
- A dataset must use a single builder version, and it must equal the manifest's version when
  the manifest names one (added in the Task 3 review: before, only `load_dataset` checked this).
- **New `_check_share_links`** runs for any record with a link in its state *or* a link action:
  - link ids must be contiguous from `lnk-0001`;
  - every stored witness must replay from the post-action state (exact witness to canonical
    equality in exactly `restore_depth` steps; approximate witness to core equality);
  - a depth without a witness is an error.

**End-to-end test (in-memory fixtures).** One scenario per family (6 records) is built in
memory and written only to pytest's temporary directory. The test then checks:
- `load_dataset` works, and the probe and stated prompts rebuild and hash-check as 1.1.0;
- every link's id, address, access, custom/generated and active/revoked appears in the user
  turn, and both link tools appear in the tool list;
- no witness call and no "reversib" appears in the probe prompt;
- `validate_directory` reports 0 errors, including its leakage-token check.

## 5. Per-horizon audit (`s03` other access, and every state)

`horizon_audit` re-runs the oracle separately with `horizon = h` for h = 1, 2, 3 and replays
the witnesses. Required evidence per label:
- **R:** an exact witness of at most h steps that replays to canonical equality.
- **P:** an approximate witness of at most h steps that replays to core equality but *not* to
  canonical equality, **and** a search that is exhaustive through depth h with no exact witness.
  The residual is listed.
- **I:** an exhaustive search with neither witness.

Each per-horizon label must also equal the primary (h = 3) assessment's label at h.

**`s03` other access, all 7 members:**
- **h = 1 and h = 2:** P. The approximate witness is one step (`revoke_share_link`). Its
  residual is exactly the revoked record's access (`access: view -> edit` or the reverse). The
  search is exhaustive through h with no exact witness.
- **h = 3:** R, with a 3-step exact witness (`revoke → create(old access) → revoke`) that
  replays to canonical equality.

So s03 satisfies the definitions and is included.

**All 42 planned states pass at every horizon:**

| h | R | P | I |
|---|---|---|---|
| 1 | 14 | 28 | 0 |
| 2 | 14 | 28 | 0 |
| 3 | 21 | 21 | 0 |

Labels by horizon:
- R R R: 14
- P P P: 21
- P P R: 7

**No unexpected label changes.** All 42 match their declared expectation. 0 gate drops.

## 6. Gold-entry gates (link-id allocation, malformed states)

`gold_gate` applies these checks in order; the first failure is the recorded drop reason:
1. **Well-formed state:** `validate_state`, an exact `from_dict(to_dict)` round trip, and link
   ids contiguous from `lnk-0001`.
2. No pending timers.
3. **The judged action succeeds.** An id-allocation refusal is named
   `link_id_allocation_failed`; other refusals are named `judged_action_failed: <code>`.
4. A definitive oracle.
5. Per-horizon evidence (§5).

If either member fails, the **whole pair** is dropped and counted, so no orphan pivot can enter.

**Tests:**
- duplicate active addresses are rejected (`invalid_state`);
- id gaps are rejected (`link_ids_not_contiguous`);
- with the shape check bypassed, the allocation refusal is still caught and named;
- a forced member failure drops its pair.

The validator independently re-checks contiguity and witness replay (§4), so a hand-built
record that skipped the gates is still caught.

## 9. Readiness and accepted scientific limitations

**Engineering: ready to freeze.**
- Counts reconcile: 3 families, 21 base scenarios, 21 minimal pairs, 42 states, 42 records.
- All planned states pass all gates with complete per-horizon evidence, and there are no
  expectation or declaration mismatches.
- 1.1.0 records load, rebuild and validate end to end.
- The legacy paths are unchanged.

**Accepted scientific limitations (approved in Phase 5E Task 3):**
1. **SD1 is mechanically inflated.** No record in the named priors has a `share_links` field
   or a link tool, so SD1 = 1.0 by construction. It carries no evidence of diversity.
2. **SD2 and SD3 are weak in this small planned sample.** The planner de-duplicates coarse
   structure, so SD2 = 1 by construction. With 42 states and no shared scenarios with the
   priors, SD3 = 0 has little power to detect conflicts.
3. **No irreversible examples are expected.** The policy-blocked irreversible case is excluded
   by design, so h3 labels are 21 R / 21 P. The pilot must not be used for class-balanced
   metrics or three-class claims.
4. **The 42 records are diagnostic coverage, not 42 independent mechanisms.** They carry 5
   recovery signatures, one of which (`create → approx: revoke`) is shared by the absent
   members of `s02` and `s03`. Background variation makes the states structurally distinct, not
   mechanistically distinct.

**s03 labels are horizon-relative.** A label is defined *relative to the horizon h*: R if exact
restoration exists within h steps, P if only approximate restoration does. The `s03`
other-access states are exactly restorable in 3 steps, so they are:
- **P at h = 1 and h = 2**, where only the 1-step approximate witness fits and no exact witness
  exists within h;
- **R at h = 3**.

The R at h = 3 holds only because the primary horizon equals the exact depth, and it would not
survive a horizon of 2. Every analysis of this pilot reports h1, h2 and h3 separately and must
not treat the h3 label as an intrinsic property of the action.

Freezing still needs the reviewer to set `frozen_at_utc` and `base_commit` (the Task 3 commit)
and to add a sha256 file. Only then may records be generated.

## 10. Scientific limitations

1. The four accepted limitations and the horizon-relative `s03` labels (§9).
2. **The labels inherit the three simulator assumptions** in the manifest (custom
   re-activation, non-core generated identity, token reservation).
3. **The custom/generated marker is shown explicitly** in the state text. This is faithful and
   it is the pivot, but it is easy to read; the `gen-…` token format reveals it anyway.
4. **The design table and the judge share the simulator.** Their agreement checks the rules,
   not the realism of the semantics.
5. **All values here are planned, in-memory values.** None is dataset-scale evidence.
6. **The end-to-end fixtures cover one scenario per family.** The full plan is validated in
   memory only by the draft script.
